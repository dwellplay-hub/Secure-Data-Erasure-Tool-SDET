FULL PROJECT PROMPT: SDET DEVELOPMENT (PERFECT ALIGNMENT)

Secure Data Erasure Tool (SDET)NIST SP 800-88 Rev. 2–Aligned, File-Level Secure Deletion Tool

1. Project Overview

Build a cross-platform Secure Data Erasure Tool (SDET) implemented entirely in Python, providing both:


A Command-Line Interface (CLI)

A Modern Graphical User Interface (GUI) using customtkinter (NOT standard Tkinter).

The tool performs file-level logical sanitization in compliance with NIST SP 800-88 Rev. 2 (CLEAR), while also educationally supporting legacy overwrite methods (Gutmann and DoD) with clear warnings. The tool must explicitly distinguish between modern, recommended practices and deprecated legacy techniques, and must not claim hardware-level sanitization.

2. NIST SP 800-88 Compliance Model

The project must strictly follow the NIST SP 800-88 Rev. 2 sanitization taxonomy:


NIST CLEAR: ✅ Fully implemented (Default, recommended secure deletion)

NIST PURGE: ⚠ Explained only (Informational guidance on firmware tools)

NIST DESTROY: ❌ Out of scope (Physical destruction, documented only)

Gutmann 35-pass: ⚠ Legacy / Educational only (Demonstration, not recommended)

DoD 3 / 7-pass: ⚠ Legacy / Deprecated (Demonstration, not recommended)

3. Operating Modes

The tool must implement explicit modes:


3.1 Default Mode: NIST Clear (REQUIRED)

This must be the default mode. It must perform:

✔ 1-pass random overwrite (user-addressable sectors only)

✔ Flush + fsync / FlushFileBuffers to ensure write completion to physical disk

✔ File truncation to zero length

✔ Directory entry removal (unlink)

✔ Optional filename randomization (Metadata Obfuscation)

✔ Ethical logging using SHA-256 anonymized identifiers

⚠ The tool must explicitly state that NIST Clear is a logical sanitization, not firmware-level erasure.

4. Legacy Methods (Educational Only)


4.1 Gutmann 35-pass: Implement the exact original Gutmann 35-pass pattern. Label clearly in CLI/GUI: ⚠ LEGACY METHOD – EDUCATIONAL ONLY. Not recommended for SSDs. Ineffective due to wear leveling. May reduce SSD lifespan.

4.2 DoD 3-pass / 7-pass: Implement DoD overwrite sequences. Clearly mark as: ⚠ DEPRECATED – NOT RECOMMENDED. Obsolete per NIST SP 800-88 Rev. 2.

5. NIST Purge (Information-Only Mode)

SDET must NOT attempt to perform purge. Instead, it must:


Display an informational message explaining why software overwrite is imperfect on SSDs (due to Flash Translation Layer & Wear Leveling).

Recommend external firmware tools (e.g., nvme-cli, hdparm --security-erase, vendor utilities).

6. Command-Line Interface (CLI) Requirements


Default Behavior: python sdet_cli.py --file secret.txt ➡ Automatically uses NIST Clear mode.

Explicit Flags:--nist clear (Default)--legacy gutmann--legacy dod3--legacy dod7--purge-info (Explain only)

Other Flags: --recursive, --randomize-name, --cleanup-logs, --no-confirm

7. GUI Requirements (CustomTkinter) - DUAL MODE & MODERN UX

The GUI MUST be built using the customtkinter library to achieve a sleek, modern, premium look. Standard tkinter widgets should be strictly avoided.


7.1 Modern Styling Rules:

Force Dark Mode: customtkinter.set_appearance_mode("dark")

Use a modern color theme (e.g., "blue" or "dark-blue").

Use card-based layouts (CTkFrame with corner_radius=10 or 15).

Use modern toggle switches (CTkSwitch) for options like "Randomize Filename" and "Recursive (Folder Deletion)".

Ensure ample padding (padx, pady) so the UI breathes and does not look cluttered.

7.2 Normal Mode (For General Users):

Clean, non-technical interface.

Offers a simple, prominent "Secure Delete" button (CTkButton) (silently executes NIST Clear).

Displays simplified, easy-to-understand SSD warnings.

7.3 Advanced Mode (For IT/Educational Use):

Exposes explicit algorithms: ✅ Recommended (NIST SP 800-88 Clear), ⚠ Legacy – Not for SSDs (Gutmann / DoD), ℹ NIST Purge – Information Only.

Use a clean, selectable list or segmented button (CTkSegmentedButton). Includes Badges/Colors for warnings.

7.4 Safe Mode (Critical Path Blacklisting) - MANDATORY:

Implement a hardcoded blacklist of critical system directories (e.g., C:\Windows, C:\Program Files, /bin, /boot, /etc).

If selected, block the action and display an "Accidental Deletion Blocked" error.

7.5 Asynchronous Execution (Multi-threading):

The erasure engine MUST run on a separate background thread (threading.Thread) to prevent the GUI from freezing during large file operations (e.g., 35-pass Gutmann). Use a modern progress bar (CTkProgressBar).

7.6 GUI Safety Requirements:

Explicit confirmation dialogs before any deletion.

No silent destructive actions.

7.7 Safe Exit Protocol (Fail-Safe):

The application must safely handle termination during active erasure processes.

Intercept the window close event (WM_DELETE_WINDOW protocol).

If an erasure is actively running in the background thread, trigger a warning dialog ("Erase in Progress. Are you sure you want to exit?") to prevent data corruption.

Include a dedicated visible "Exit" button in the UI that triggers this exact same safe exit logic.

8. Ethical Logging & Visual Privacy (MANDATORY)

SDET must handle logging in two distinct ways to preserve privacy:


8.1 Physical Audit Log File (.sdet_audit.log):

✔ Log SHA-256 hashes of file paths/filenames, NOT plaintext names.

✔ Log timestamp, method used, pass count, and success/failure result.

✔ Never log raw file paths. Support secure deletion of the log file itself.

8.2 In-Memory UI Activity Log (Visual Privacy):

✔ The on-screen GUI log must employ "Masking" for filenames to prevent shoulder surfing (e.g., secret.txt should be displayed as sec***.txt).

✔ Use a modern scrollable text box (CTkTextbox).

✔ This visual log must only exist in RAM and clear when the app closes.

9. Technical Constraints (IMPORTANT)

✅ Python 3.7+

✅ Libraries: Standard libraries + customtkinter

❌ No standard Tkinter widgets (tk.Button, tk.Frame - use CTkButton, CTkFrame instead)

❌ No kernel drivers

❌ No firmware-level commands

❌ No false claims of PURGE or DESTROY capabilities.

10. Educational & Academic Positioning

The codebase and UI must:


Demonstrate why legacy methods are obsolete.

Explain SSD behavior (wear leveling, FTL).

Emphasize correctness, transparency, and ethics.

11. Outcome Statement

The Secure Data Erasure Tool (SDET) fully implements NIST SP 800-88 Rev. 2 CLEAR sanitization at the file-system level. Legacy overwrite techniques are included strictly for educational comparison. Hardware-level sanitization methods such as PURGE and DESTROY are intentionally out of scope due to firmware and physical access requirements.
